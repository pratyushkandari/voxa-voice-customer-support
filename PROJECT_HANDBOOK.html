What Voxa is

Voxa is a customer-support assistant for a fictional electronics shop (also called Voxa) that sells earbuds, headphones, microphones and webcams. A customer opens a web page, types or speaks a question, and gets an answer that appears word by word, like a chat app.

The problem it addresses

Support teams answer the same questions all day: Where is my order? Can I get a refund? What is the warranty? Voxa automates those answers, looks up live order data in a database, and creates a ticket for a human when the customer is angry or asks for a person.

Who uses it

  • Customers — the chat console at /chat.
  • Support operators / admins — the operations console at /admin (metrics and escalation tickets).
  • API clients — REST, Server-Sent Events and WebSocket endpoints documented by FastAPI at /docs.

Honest framing you should use in interviews

Voxa is a portfolio / demonstration system. Say this plainly; interviewers respect accuracy far more than inflated claims.

Executive summary

In plain language

Voxa is a chat website backed by a Python server. When you send a message, the server cleans it (hides card numbers, blocks "ignore your instructions" tricks), decides what kind of question it is, fetches the answer from a database or a cache, and streams it back word by word over a permanent connection called a WebSocket. Slow jobs such as turning audio into text run in separate background programs ("workers") that pick tasks from a queue. If things start failing, a "circuit breaker" stops sending work downstream for 15 seconds and shows a polite fallback instead of hanging. Everything runs as Docker containers, and you deployed the whole set on one Azure virtual machine.

Technical summary

  • Gateway: FastAPI (Python 3.11 in Docker) exposes REST, Server-Sent Events (SSE) and a full-duplex WebSocket at /v1/ws/stream. Text queries over the WebSocket are answered in-process by a priority-ordered deterministic intent router (voxa-backend/app/main.py:352–444 (answer_text_query)).
  • Asynchronous workers: STT (Faster-Whisper, INT8 on CPU), "LLM" (tool routing + pgvector retrieval, no generative model), TTS (edge-tts) and a supervisor, connected by Redis Streams consumer groups; results return through per-session Redis Pub/Sub channels.
  • Data: PostgreSQL 16 with the pgvector extension and an HNSW index for 384-dimensional embeddings (all-MiniLM-L6-v2); Redis 7 for streams, Pub/Sub, a semantic answer cache (cosine ≥ 0.92), rate-limit logs and circuit-breaker state.
  • Resilience: Redis-backed three-state circuit breaker with a single half-open probe, sliding-window rate limiter in Lua, retry → dead-letter queue after 3 attempts, and pending-entry reclaim for crashed workers.
  • Security: bcrypt passwords, HS256 JWTs, admin role check, ownership checks on conversations and feedback, regex PII masking and prompt-injection neutralisation, payload size limits.
  • Frontend: Next.js 14 (App Router, React 18, TypeScript, Tailwind) with landing, chat and admin pages.
  • Operations: Prometheus metrics at /metrics, Prometheus and an empty Grafana in Compose, Kubernetes manifests (not verified as applied), 36 passing unit/regression tests plus 6 opt-in end-to-end tests.
  • Deployment: User-reported single Azure Linux VM running docker compose; git history contains the VM's Azure public IP configured as the frontend's API URL (details in Azure deployment).

Interview pitches (30 seconds, 2 minutes, 5 minutes)

Every sentence below is backed by code. Practise them aloud; then adapt the words so they sound like you.

30-second version

"I built Voxa, a real-time customer-support platform. A Next.js console talks to a FastAPI gateway over a WebSocket and streams answers word by word. Order and refund questions are answered from PostgreSQL, policy questions use embedding search with pgvector plus a Redis semantic cache, and slow work like speech-to-text runs in separate workers connected by Redis Streams. I added a Redis-backed circuit breaker, rate limiting and a dead-letter queue, and deployed the whole Docker Compose stack on an Azure Linux VM."

2-minute version

Problem. "Support teams answer the same order, refund and policy questions repeatedly, and users expect instant, streaming answers."

Architecture. "The browser keeps one WebSocket open to a FastAPI gateway. Each text message goes through a rate limiter, a guardrail that masks card numbers and neutralises prompt-injection phrases, and a circuit breaker. A deterministic intent router then handles it: order IDs trigger a SQL lookup, anger or 'talk to a human' creates a support ticket, and generic questions are embedded with a sentence-transformer model and matched first against a Redis semantic cache and then against a pgvector HNSW index."

Async pipeline. "Audio and the REST SSE endpoint use Redis Streams consumer groups: an STT worker runs Faster-Whisper in INT8 on CPU, an answer worker does tool routing and retrieval, and a TTS worker uses edge-tts. Workers publish tokens to a per-session Pub/Sub channel, so any gateway replica can relay them."

Reliability. "Workers acknowledge only after finishing, retry up to three times and then dead-letter; a supervisor reclaims tasks stuck with crashed workers. The circuit breaker state lives in Redis so every replica agrees."

Honest limits. "There is no generative LLM yet — the model name is reserved but not loaded — and the web console uses browser speech recognition rather than the server STT path. I deployed it with Docker Compose on a single Azure VM; the next steps would be HTTPS, managed databases and proper load testing."

5-minute version (structured walkthrough)
  1. Context (30 s): fictional electronics shop; three audiences (customers, admins, API clients); goal: fast, streaming, reliable answers.
  2. Request path (90 s): walk through one WebSocket text_query: JSON validation and size limit → rate limit (Lua sliding window in Redis) → sanitize_user_input → circuit_breaker.can_execute → answer_text_query priority list → stream words with ttft_ms and trace_id → final frame → persist both messages for signed-in users. Point at voxa-backend/app/main.py:555–641.
  3. Retrieval (60 s): 384-dimensional normalised embeddings, cosine similarity as a dot product, Redis cache threshold 0.92, pgvector <=> cosine distance with an HNSW index, similarity cut-off 0.35, and why order data is never cached.
  4. Async workers (60 s): Redis Streams vs Kafka trade-off; consumer groups; acknowledge-after-processing gives at-least-once delivery; retry counter carried in the payload; DLQ; supervisor uses XPENDING/XCLAIM.
  5. Operations (30 s): Prometheus metrics labelled by route template to keep cardinality bounded; admin metrics computed from the database (percentile_cont for p95) and Redis (XINFO GROUPS pending + lag).
  6. Deployment and limits (30 s): Docker Compose on one Azure VM, plain HTTP; known gaps: no generative model, voice path bypasses guardrails, single point of failure, no TLS. Finish with what you would do next.

Primary execution flow (typed question)

  1. The landing page calls POST /v1/auth/guest-demo, stores the JWT in localStorage, and opens /chat (voxa-frontend/app/page.tsx:38–61).
  2. The chat page opens ws://<host>:8088/v1/ws/stream?token=… and reconnects with capped exponential backoff (voxa-frontend/app/chat/page.tsx:214–236).
  3. The user sends {"type":"text_query","text":…,"trace_id":…} (voxa-frontend/app/chat/page.tsx:284–304).
  4. The gateway validates size, applies the rate limit, sanitises, checks the breaker, calls the router, streams one frame per word, then a final frame with telemetry (voxa-backend/app/main.py:555–614).
  5. For signed-in users (guests count, because they have a token), the user and assistant messages are saved in PostgreSQL (voxa-backend/app/main.py:616–641).
  6. The browser appends tokens to the bubble with the same trace_id and updates the telemetry HUD (voxa-frontend/app/chat/page.tsx:140–212).

Top limitations to know by heart

  1. No generative model: "LLM worker" is a misnomer for a deterministic tool-and-retrieval worker (voxa-backend/workers/llm_worker.py:1–11).
  2. Two separate routers: the WebSocket router and the worker router answer the same question differently (details).
  3. The server voice path skips PII masking and the circuit breaker.
  4. Single VM, plain HTTP, default passwords unless overridden: fine for a demo, not production.
  5. The semantic cache compares against at most 50 sampled entries with a linear scan.

B. Architecture and workflows, end to end

Each journey below follows real function calls. Read them with the source open beside you.

Start-up sequence (gateway)

  1. Uvicorn imports app.main. Importing modules creates singletons: settings, the async engine (no connection yet), and Redis clients inside rate_limiter, circuit_breaker, queue_manager and rag_engine (redis-py connects lazily on first command).
  2. lifespan runs init_db(): pgvector extension, tables, HNSW index (voxa-backend/app/main.py:83, voxa-backend/app/database.py:42–64).
  3. seed_database() inserts demo users, orders and embedded knowledge-base rows if missing; errors are logged as a "notice" because replicas may race (voxa-backend/app/main.py:84–88).
  4. Consumer groups are created on the four streams (voxa-backend/app/main.py:89–92).
  5. The embedding model is loaded by embedding the text "warm-up", so the first real user does not wait for it (voxa-backend/app/main.py:93–97).
  6. yield — the server now accepts traffic. On shutdown, engine.dispose() closes pooled DB connections (voxa-backend/app/main.py:98–100).

Compose starts the gateway only after Postgres and Redis pass their health checks (docker-compose.yml:70–74). Workers start independently and create their own consumer group if needed, then loop forever.

Journey A — open the site and get a guest identity

  1. Browser loads the landing page; a fetch to /health drives the status dot.
  2. Click "Start Live Support Session" → POST /v1/auth/guest-demo. That route is rate-limited by IP (no token yet) (voxa-backend/app/main.py:183–188).
  3. create_guest_user inserts a user with a random email and random bcrypt-hashed password, then signs a JWT with sub = user UUID and role = user.

Journey B — typed question over the WebSocket (the main path)

  1. Receive and validate. Only text frames; JSON object required; unknown types get an error frame but the socket stays open (voxa-backend/app/main.py:508–524, voxa-backend/app/main.py:643–644).

  4. Circuit breaker. If OPEN (or HALF_OPEN and the probe is taken) a single final frame with the fallback text is sent (voxa-backend/app/main.py:569–580).
  5. Route. answer_text_query(raw, clean, user_id) walks the priority list below; exceptions are counted as breaker failures and replaced by an apology (voxa-backend/app/main.py:582–589).
  6. Stream. ttft_ms is measured once routing is done, then one frame per space-separated word with a 30 ms sleep, then the final frame (voxa-backend/app/main.py:591–614).
  7. Persist. For token holders: create the conversation on the first turn, then add the (masked) user message and the assistant message with latencies (voxa-backend/app/main.py:616–641).

C. Technologies explained (only the ones really used)

Each technology gets three levels: Core (what it is, simply), In Voxa (where and how this repository uses it), and Interview extension (internals, trade-offs, alternatives).

Direct vs transitive vs dev dependencies

Direct dependencies are listed in requirements*.txt or package.json and imported by project code (FastAPI, SQLAlchemy, redis…). Transitive ones arrive because a direct dependency needs them (Starlette under FastAPI, PyTorch under sentence-transformers, CTranslate2 under faster-whisper, numpy under pgvector). Dev/test-only: pytest, pytest-asyncio, httpx (TestClient), eslint, typescript. Listed but unused in V2 code: loguru, python-multipart, transformers (root file only).

FastAPI, Uvicorn and asyncio

Core

FastAPI is a Python web framework: you write functions, decorate them with a URL, and it handles parsing, validation and JSON. Uvicorn is the server program that listens on a port and hands each request to FastAPI using the ASGI standard. asyncio lets one Python thread juggle thousands of connections: while one request waits for the database, the thread serves another. Analogy: one waiter taking many tables' orders instead of standing at the kitchen door for each dish.

In Voxa

All routes are async def. Dependencies (Depends(get_db), Depends(get_current_user), Depends(rate_limit_dependency)) inject sessions, users and checks (voxa-backend/app/main.py:193–199). The lifespan context manager handles start-up and shutdown. CPU-heavy work (bcrypt, embeddings, Whisper) is pushed to threads with asyncio.to_thread so it does not freeze the event loop (voxa-backend/app/auth.py:37–44). One Uvicorn worker per container (voxa-backend/Dockerfile.gateway:27–29) because Prometheus metrics are kept in process memory.

Interview extension

Async helps I/O-bound work, not CPU-bound work: a blocking call inside async def stalls every connection on that process — that is why the code offloads to threads. The GIL means threads give concurrency, not parallel Python bytecode, but bcrypt and PyTorch release the GIL in native code. Alternatives: Flask (synchronous; used in V1; WebSockets need extensions), Django Channels (heavier), Node.js (single language with the frontend), Go (cheaper concurrency). Switching to Flask would mean thread-per-request and losing native WebSocket/SSE ergonomics.

WebSockets and Server-Sent Events (SSE)

Core

Normal HTTP is "ask once, get one answer". A WebSocket upgrades one HTTP connection into a two-way pipe that stays open, so both sides can send messages at any time. SSE is one-way: the server keeps an HTTP response open and writes data: … lines as events happen.

In Voxa

The console uses /v1/ws/stream with JSON text frames (text_query, audio_chunk in; token_chunk, ack, audio_response, error out). POST /v1/chat/completions returns text/event-stream built by sse_event (voxa-backend/app/main.py:125–127). The browser reconnects the WebSocket with exponential backoff.

Interview extension

WebSockets are stateful, so load balancers need connection affinity or a shared back-channel; Voxa's per-session Redis Pub/Sub channel is that back-channel for worker results. SSE works through ordinary HTTP infrastructure and auto-reconnects in browsers (EventSource) but is server→client only and EventSource cannot send an Authorization header. Long polling is the fallback when neither is allowed. Note: passing the JWT in the WebSocket URL is common because browsers cannot set headers on new WebSocket(), but URLs can end up in logs.

PostgreSQL, SQLAlchemy 2 (async) and asyncpg

Core

PostgreSQL is a relational database: tables, rows, foreign keys and transactions that are all-or-nothing. SQLAlchemy is an ORM — you work with Python classes and it writes SQL. asyncpg is the async driver that talks to PostgreSQL without blocking.

In Voxa

Seven tables; request-scoped sessions via get_db; background sessions via AsyncSessionLocal() inside the WebSocket loop and workers. The vector search is raw SQL through text() because it uses the pgvector operator (voxa-backend/app/rag_engine.py:68–75). Pool: 20 connections + 10 overflow per process.

Interview extension

Pool maths matters when scaling: 3 gateway replicas × 30 + workers can approach PostgreSQL's default max_connections of 100 — a reason to add PgBouncer. expire_on_commit=False avoids lazy reloads after commit (lazy loads are awkward in async code). Without Alembic, schema changes need manual SQL. Alternatives: MySQL (no pgvector), MongoDB (flexible documents, weaker joins), a separate vector DB (extra system to keep consistent).

Redis (Streams, Pub/Sub, Lua, keys with TTL)

Core

Redis is an in-memory data store: very fast reads and writes of strings, lists, sorted sets and more. Voxa uses it as a shared whiteboard that all containers can see.

In Voxa
  • Streams (append-only logs with consumer groups) for worker tasks: XADD, XREADGROUP, XACK, XPENDING, XCLAIM.
  • Pub/Sub for streaming worker output back to the gateway.
  • Sorted sets + Lua for the rate limiter; strings with TTL for the breaker, cache, heartbeats and counters.
  • Compose runs Redis with append-only-file persistence (docker-compose.yml:38).
Interview extension

Pub/Sub is fire-and-forget: a message published while nobody listens is lost (hence subscribe-before-publish). Streams persist entries and track who has what (pending entries list), which enables at-least-once delivery. Redis executes commands on a single thread, which is why a Lua script is atomic. Risk: Redis is now a dependency of nearly every request — a single point of failure in this deployment. Alternatives: Kafka/RabbitMQ for queues, Memcached for caching, a dedicated rate-limit service.

JWT (python-jose) and bcrypt (passlib)

Core

bcrypt turns a password into a slow, salted hash so a stolen database does not reveal passwords. A JWT is a signed token: header.payload.signature. Anyone can read the payload, but only someone with the secret can create a valid signature.

In Voxa

HS256 (HMAC-SHA256, one shared secret), 24-hour expiry, payload {"sub": user_uuid, "role": …, "exp": …}. The server looks up the user on every authenticated request, so a deleted user is rejected even with a valid token (voxa-backend/app/auth.py:78–96).

Interview extension

HS256 means every service that verifies tokens holds the signing key; RS256/ES256 lets verifiers hold only a public key. There is no refresh token or revocation list; logout is client-side. The role claim is inside the token, but admin checks read user.role from the database, which is safer. Alternatives: server-side sessions in Redis (easy revocation), OAuth/OIDC providers.

Data model

Constraints, indexes and transactions

  • Indexes: unique index on users.email; indexes on every user_id/conversation_id foreign key column that sets index=True; composite (conversation_id, created_at) for reading a thread in order; HNSW on embeddings. feedback_ratings foreign keys are not indexed.
  • Cascades: deleting a user deletes their conversations → messages → feedback (ON DELETE CASCADE). Tickets and orders reference users without an ON DELETE rule, so PostgreSQL rejects deleting a user who still has tickets.
  • Transactions: each await db.commit() is a separate transaction. In the WebSocket path the conversation is committed first, then both messages in a second commit; a crash between them leaves an empty conversation (harmless).
  • Not enforced in the database: allowed values for role/status/priority, score range (validated by Pydantic only).

Important queries

-- Knowledge-base search (rag_engine.py)

FROM knowledge_base

E. AI and ML components

Correct this misconception first

Voxa V2 has no generative language model. Nothing writes new sentences. Answers are (a) fixed texts chosen by keyword rules, (b) formatted database results, or (c) a stored knowledge-base passage returned word for word. The "LLM worker" name and LLM_MODEL_NAME describe a planned design; the worker logs that the model "is not loaded" (voxa-backend/workers/llm_worker.py:60–63). The machine-learning parts that do run are: a sentence-embedding model, vector similarity search, Whisper speech recognition, and a remote text-to-speech service. The V1 notebook did fine-tune a generative model, but V2 does not use it.

AI vs ML, in this project's terms

Artificial intelligence is the broad goal of software doing tasks that seem to need intelligence (here: understanding a question). Machine learning is one way to get there: models whose behaviour is learned from data instead of hand-written rules. Voxa mixes both: hand-written rules (the router) and pretrained ML models used only for inference (applying a trained model). No training happens in V2; training happened only in the V1 notebook.

Embeddings

Core

An embedding is a list of numbers that represents the meaning of a text. Texts with similar meaning get lists that point in a similar direction. "How long is delivery?" and "When will my package arrive?" share few words but land close together.

In Voxa

generate_embedding returns 384 float32 numbers, normalised to length 1 (voxa-backend/app/rag_engine.py:47–53). The model is loaded lazily the first time it is needed and warmed up at gateway start. Each call runs in a thread. Knowledge-base documents are embedded once at seeding (voxa-backend/app/seed_data.py:97–110).

Interview extension

MiniLM-L6 is a small 6-layer transformer distilled for sentence similarity: fast on CPU, decent quality, English-centric, and it truncates long inputs (its maximum sequence length is 256 word-pieces). On a miss, a WebSocket question is embedded up to three times — cache check, KB search, cache store — because each function embeds independently (voxa-backend/app/main.py:433–443). Passing the vector through would remove two thirds of that CPU work. Bigger models (e.g. 768-d) improve accuracy but cost more CPU, memory and storage.

Cosine similarity as a dot product

Cosine similarity measures the angle between two vectors: cos(u,v) = (u·v) / (|u|·|v|). Because every vector here has length 1, the denominator is 1 and similarity is just the dot product u·v = Σ uᵢvᵢ (voxa-backend/app/rag_engine.py:116–117).

Tiny example (2-D instead of 384-D): u = (0.6, 0.8), v = (0.8, 0.6). Both have length 1. u·v = 0.48 + 0.48 = 0.96 → very similar. w = (0, 1): u·w = 0.8 → less similar. pgvector's <=> returns distance = 1 − similarity, which is why the SQL computes 1 - (embedding <=> …).

The semantic cache

Core

A normal cache answers only identical questions. A semantic cache also answers questions that mean the same thing, by comparing embeddings.

In Voxa
  1. Embed the (sanitised) question.
  2. SCAN keys matching semcache:* until 50 are collected; one MGET fetches their JSON payloads.
  3. For each payload, dot product with the stored vector; the first one ≥ 0.92 is a hit (increments local and Redis counters).
  4. On a miss the caller computes an answer and stores {query, vector, response} under semcache:<first 16 hex of sha256(lower(query))> for 1 hour.

Evidence: voxa-backend/app/rag_engine.py:87–146.

Interview extension
  • Complexity: O(k·d) per lookup with k ≤ 50 entries and d = 384 → at most ~19,200 multiply-adds; cheap in CPU, but the data transfer is not: each payload stores 384 floats as JSON text. Estimate: ~20 characters per float → ~8 KB per entry → up to ~400 KB pulled from Redis per lookup.
  • Correctness limit: SCAN order is hash-slot order, so once there are more than 50 entries the sample is arbitrary and a matching entry can be missed (the code comment says so, voxa-backend/app/rag_engine.py:17–20).
  • "First match" not "best match": the loop returns the first entry over the threshold, not the most similar one.
  • Better designs: Redis Stack vector search (HNSW inside Redis), or a pgvector table for cache entries; both give indexed nearest-neighbour lookups.
  • Why order data is never cached: answers that depend on the user or create side effects (tickets) must not be served to someone else; only router rule 12 touches the cache, and REST checks detect_tool_intent (voxa-backend/app/main.py:215–217).

Vector search with pgvector and HNSW

Core

pgvector adds a vector column type and distance operators to PostgreSQL. HNSW (Hierarchical Navigable Small World) is an index shaped like a multi-level graph: searches start at a sparse top layer and greedily hop to closer neighbours layer by layer, so they inspect a small fraction of rows.

In Voxa

Index created at start-up with default parameters (voxa-backend/app/database.py:58–63); the router asks for the top 2 passages and uses the first if similarity > 0.35, otherwise a generic answer (voxa-backend/app/main.py:437–442).

Interview extension

HNSW is approximate: it can miss the true nearest neighbour; recall is tuned with hnsw.ef_search at query time and m/ef_construction at build time. Alternative index: IVFFlat (needs training data, cheaper build). Alternatives to pgvector: Pinecone, Milvus, Qdrant, Weaviate, FAISS — better at very large scale, but data lives in a second system. The thresholds 0.92 and 0.35 are hand-picked constants; the repository has no labelled evaluation set, so their quality is unmeasured.

Is this RAG?

Retrieval-augmented generation means: retrieve relevant documents, put them into a language model's prompt, and let the model generate an answer grounded in them. Voxa does the retrieval half (embedding + vector search) and then returns the passage itself. The accurate name is retrieval-based answering or "the retrieval layer of a RAG system". The README and code call it RAG; in an interview say: "It implements the retrieval tier of RAG; the generation tier is designed for but not implemented."

Speech-to-text: Faster-Whisper with INT8

Core

Whisper is an open speech-recognition model from OpenAI. Faster-Whisper re-implements it on CTranslate2, an inference engine optimised for CPUs and GPUs. INT8 quantisation stores weights as 8-bit integers instead of 32-bit floats: roughly a quarter of the memory and faster maths, at a small accuracy cost.

In Voxa

WhisperModel("base", device="cpu", compute_type="int8"); audio is written to a temporary file (FFmpeg detects the container), transcribed with beam_size=2, segments joined (voxa-backend/workers/stt_worker.py:45, voxa-backend/workers/stt_worker.py:56–72). Inference runs in a thread so heartbeats continue.

Interview extension

The whole utterance is uploaded and transcribed at once — not streaming recognition, so latency grows with audio length. Larger Whisper sizes are more accurate but slower; GPUs change the trade-off. README admits accuracy and latency were not benchmarked. A long transcription (> 15 s) could be reclaimed by the supervisor while still running, causing duplicate work.

Text-to-speech: edge-tts

edge-tts is an open-source Python client for Microsoft Edge's online "Read aloud" neural voices. It is free and sounds natural, but it is an unofficial use of a remote service: no SLA, needs outbound internet, and could change without notice. For production you would use a supported API (for example Azure AI Speech) or a local model such as Piper. Voxa treats TTS as best-effort: failures are logged and acknowledged without retry (voxa-backend/workers/tts_worker.py:70–74).

The V1 notebook: fine-tuning FLAN-T5

  • Training vs inference: training adjusts model weights using examples; inference uses fixed weights to answer. V1 did training (in Colab); V2 does only inference.
  • Data: Bitext customer-support dataset, 26,872 instruction/response pairs, split 80/20 with seed 42.
  • Tokenisation: inputs "Answer the customer query: " + instruction and responses are tokenised, padded/truncated to 128 tokens; response token IDs become labels.
  • Setup: 2 epochs, batch size 2 with gradient accumulation 4 (effective 8), learning rate 2e-4, fp16 off. Stored output: training finished in 63 minutes 8 seconds.
  • Caveats to mention honestly: padded label positions are not replaced with -100, so the loss also trains on padding tokens; no evaluation metric values are printed (only an HTML progress widget); the saved directory name (voxa_model_cpu) differs from what backend.py loads (model3).

Adding a real LLM Proposed

  1. In LLMWorker.generate_response, keep tool routing; for generic questions, retrieve the top-k passages and build a prompt with sanitize_and_isolate_prompt (already written for this purpose).
  2. Run the model either locally (e.g. a small instruction model via llama.cpp or vLLM; needs RAM/GPU) or via a hosted API (latency, cost per token, data-privacy review).
  3. Stream real tokens to Pub/Sub instead of splitting a finished string, so TTFT becomes a genuine first-token time.
  4. Add an evaluation set (questions + expected facts) to measure groundedness and to tune the 0.35 threshold.
  5. Keep the circuit breaker and timeout; LLM calls are the slowest, least predictable dependency.

F. Deployment: Docker, Azure, Kubernetes, Git and GitHub

Docker and Docker Compose

Core

A Docker image is a packaged filesystem with your code, its libraries and a start command. A container is a running instance of an image, isolated from other containers. Docker Compose starts several containers from one YAML file, gives them a private network where they reach each other by service name (postgres, redis, gateway), and maps chosen ports to the host.

In Voxa
  • Three Dockerfiles: gateway, one shared worker image (four services use it with different commands), and a two-stage frontend build.
  • CPU-only PyTorch wheels are installed first to keep images small; commit 61d6e3d says this was done "to reduce image size by 90% and prevent disk exhaustion".
  • Containers run as non-root users (uid 1001, or node).
  • Health-based start order: the gateway waits for Postgres (pg_isready) and Redis (PING) to be healthy.
  • Restart policy unless-stopped on every service; named volumes for Postgres, Redis and Grafana data.
Interview extension

Compose is a single-host tool: no automatic rescheduling to another machine, no rolling updates, no autoscaling. Scaling a service with --scale is blocked here by fixed container_names (the runbook mentions this). depends_on only orders start-up; it does not restart the gateway if Postgres later dies — the gateway's pool reconnects (pool_pre_ping). Images prom/prometheus:latest and grafana/grafana:latest are unpinned, so rebuilding later can pull different versions.

What happens on reboot, crash or redeploy

  • VM reboot: if the Docker service starts at boot (the normal default on Ubuntu), containers with unless-stopped come back. Data survives in named volumes on the managed disk.
  • JWT secret unset: every gateway restart generates a new random key, so all issued tokens stop working (voxa-backend/app/config.py:78–88). Users must start a new session. Set JWT_SECRET_KEY to avoid this.
  • Model downloads: the gateway and STT worker download models into the container user's home directory, which is not a named volume, so recreated containers download again.
  • Single point of failure: if the VM stops, everything stops. There is no second VM, load balancer or backup job in the repository.

Performance and bottlenecks

  • Artificial pacing: both the gateway and the LLM worker sleep 30 ms per word. A 52-word knowledge-base answer (prefix + passage) therefore takes about 52 × 0.03 ≈ 1.6 s to stream. In the gateway this is async and costs nothing per connection; in the LLM worker it is sequential, so one worker delivers at most roughly one such answer every 1.6 s (≈ 0.6 answers/s) on the SSE path.
  • Embedding CPU: up to three embeddings per WebSocket cache miss, all on the gateway's CPU.
  • Cache transfer: up to ~400 KB per cache lookup (estimate from JSON-encoded vectors).
  • bcrypt on guest creation: every "Start session" click hashes a random password (deliberately slow, ~100–300 ms per the code comment).
  • Metrics: one Uvicorn worker per container means one CPU core per gateway container for Python code.
  • Measured numbers: none in the repository. The "<180 ms TTFT" figure is a target, and ttft_ms on the WebSocket measures time until the answer is ready (routing done), not model token generation.

Major decisions, alternatives and when another choice wins

Answer typed questions in the gateway instead of the worker

Choice: the WebSocket text path runs the router in-process (voxa-backend/app/main.py:7–9). Why it fits: rules and SQL are fast, so a queue hop would add latency and moving parts. Cost: two routers with different rules; gateway CPU now includes embeddings. Better when: answers come from a slow generative model — then every path should go through workers.

Redis Streams over Kafka or RabbitMQ

Choice: Redis Streams with consumer groups (README ADR-001). Why: one dependency already used for cache, limiter, breaker and Pub/Sub; acknowledgements and pending lists give at-least-once delivery. Cost: memory-bound, weaker durability, approximate trimming may drop unprocessed entries if the backlog exceeds ~10,000. Better when: long retention, replay, very high throughput (Kafka) or rich routing and per-message TTL (RabbitMQ).

PostgreSQL + pgvector over a dedicated vector database

Why: relational data and vectors in one transactional store; one backup; SQL joins possible. Cost: single-primary scaling limits; index builds compete with OLTP load. Better when: hundreds of millions of vectors, heavy filtering or multi-tenant vector workloads.

Deterministic rules over an LLM

Why it can be defended: predictable, fast, cheap, testable, no hallucinated refunds. Cost: brittle keyword matching ("I'm not angry" escalates via "angry" in the worker router), poor coverage of phrasing, manual maintenance. Better when: open-ended questions dominate; then combine an LLM with the same tools.

Shared Redis state for the breaker and limiter

Why: all gateway replicas agree on limits and breaker state. Cost: every request makes several Redis round trips; Redis becomes critical. Better when: a single instance — in-memory state is simpler and faster.

Docker Compose on one Azure VM

Why: same file locally and in the cloud; cheapest path to a public demo. Cost: no high availability, manual TLS, backups and patching. Better when: real users or uptime targets — use managed services or Kubernetes.

Coupling and cohesion notes

  • Good cohesion: each app/ module has one job; workers share only config, queue_manager.session_channel, agent_tools and rag_engine.
  • Coupling to watch: main.py mixes routing, business rules and persistence (788 lines); stream field names are a string contract duplicated across producer and consumers; the frontend mirrors MAX_MESSAGE_CHARS by hand.

A. Defending the project

Interviews at large product companies generally probe the same things in a project discussion, though each company and team runs its process differently: can you explain it clearly, do you understand the code you claim, can you reason about trade-offs and failures, and are you honest about limits. Use this reasoning chain for every component:

Concept → Implementation → Evidence → Trade-off → Failure → Improvement

Example (semantic cache): Concept — reuse answers for questions with the same meaning. Implementation — MiniLM embeddings, dot product ≥ 0.92 over ≤ 50 Redis entries. Evidence — rag_engine.py lines 92–130. Trade-off — cheap and simple vs linear scan and sampling. Failure — past 50 entries a match can be missed; two different questions above 0.92 could share a wrong answer. Improvement — indexed vector search, per-intent thresholds, evaluation set.

Rules for honest answers

  • Use "I" for what you did and understand. If AI tools generated code, it is fine to say you used them and then show that you understand and verified the result: "I used AI assistance for parts of the implementation; I reviewed it, fixed issues such as the STT read loop, and I can walk you through every module."
  • Never claim numbers you did not measure. "The target was under 180 ms; I didn't publish benchmarks" beats an invented "we hit 120 ms at 500 users".
  • Say "it's not implemented" crisply for the LLM, Kubernetes deployment, Grafana dashboards and HTTPS — then explain how you would add it.
  • When unsure, reason aloud from the code: "I'd expect X because the handler does Y; I'd confirm by checking Z."

Q17. What are Redis Streams and consumer groups?IntroductoryMessaging
Direct answer
A stream is an append-only log of entries (XADD). A consumer group lets several consumers share the work: each entry is delivered to one consumer (XREADGROUP), stays in that group's pending list until acknowledged (XACK).
Explanation
Pending entries make crash recovery possible: inspect with XPENDING, take over with XCLAIM.
Evidence
voxa-backend/app/queue_manager.py:32–46, voxa-backend/workers/llm_worker.py:171–196
Trade-off / limitation
Data lives in memory (with AOF persistence); approximate MAXLEN trims old entries.
Likely follow-up
"Difference from Pub/Sub?" — Pub/Sub has no storage or acknowledgement.
Q18. Explain at-least-once delivery here.IntermediateMessaging
Direct answer
Workers acknowledge only after finishing (answered, re-queued or dead-lettered). If a worker dies before XACK, the entry stays pending and is reprocessed — either by the same consumer on restart (own-PEL replay) or by the supervisor. So a task may run twice but is not silently lost.
Explanation
Exactly-once would need idempotent handlers or deduplication by message ID.
Evidence
voxa-backend/workers/llm_worker.py:93–152, voxa-backend/workers/worker_supervisor.py:32–96
Trade-off / limitation
Duplicates matter for side effects: an escalation could create two tickets.
Likely follow-up
"How would you make ticket creation idempotent?" — unique key on (trace_id) or store processed message IDs.
Q19. How do retries and the dead-letter queue work?IntermediateMessaging
Direct answer
On exception the worker re-appends the payload with retry_count+1 and acknowledges the original; when the next attempt would be the third, it writes to stream:dead:letter:queue with the error and origin stream, publishes an error event to the user, and acknowledges.
Explanation
The DLQ keeps poison messages from looping forever and preserves them for inspection.
Evidence
voxa-backend/workers/llm_worker.py:101–118, voxa-backend/tests/test_regressions.py:148–165
Trade-off / limitation
Retries are immediate (no back-off), so a transient outage can burn all three attempts in milliseconds.
Likely follow-up
"How would you add back-off?" — a delayed-retry sorted set scored by next-attempt time, or sleep before re-append.
Q20. What does the supervisor do, and what are its risks?AdvancedMessaging
Direct answer
Every 5 s it checks each group's pending list, claims entries idle ≥ 15 s, and re-appends them with an incremented attempt count — or dead-letters them after 3 attempts — then acknowledges the originals.
Explanation
It recovers work stranded by crashed consumers, whose random names never come back.
Evidence
voxa-backend/workers/worker_supervisor.py:32–96
Trade-off / limitation
Idle time is time since delivery, so a healthy worker still processing a long job (> 15 s) can have it duplicated; only 10 entries per stream per cycle; it never checks heartbeats despite its log message.
Likely follow-up
"How would you fix the long-job case?" — workers extend ownership by re-claiming their own entries periodically, or check the consumer's heartbeat before reclaiming.
Q21. Why carry retry_count in the payload instead of using Redis's delivery count?AdvancedMessaging
Direct answer
The supervisor re-appends a new entry, whose delivery count starts at 1 again. Without a counter in the payload, a message that crashes every worker would be recycled forever.
Explanation
Attempts = max(payload count, delivery count) + 1.
Evidence
voxa-backend/workers/worker_supervisor.py:68–72, voxa-backend/tests/test_regressions.py:84–105
Trade-off / limitation
Payload fields are strings; mis-parsing would raise inside the supervisor loop (caught and logged).
Likely follow-up
"Why re-append instead of XCLAIM to a live consumer?" — consumers only read their own pending list with ID 0 and new entries with ">", so re-appending is the simplest way to make the task visible to any live consumer.
Q22. Redis Streams vs Kafka vs RabbitMQ for this project?AdvancedMessaging

Explanation

Q23. What does MAXLEN ~ 10000 do and what could go wrong?IntermediateMessaging
Direct answer
Each XADD trims the stream to roughly the newest 10,000 entries (approximate trimming is cheaper). It keeps memory bounded because acknowledged entries are not deleted automatically.
Explanation
The ~ lets Redis trim whole internal nodes instead of exact counts.

Q24. Explain the circuit breaker's states.IntroductoryReliability

Q26. What is the half-open probe lock and why SET NX EX?AdvancedReliability
Direct answer
In HALF_OPEN, each request tries SET circuit:…:probe_lock 1 NX EX 10. NX means "only if absent", so exactly one request across all replicas wins and becomes the probe; EX 10 makes the lock expire if the probe dies without reporting.
Explanation
Without it, every request arriving after the cooldown would flood the recovering dependency.
Evidence
voxa-backend/app/circuit_breaker.py:74–83, voxa-backend/tests/test_regressions.py:69–79
Trade-off / limitation
If Redis errors here the code fails open and lets the request through; the OPEN→HALF_OPEN transition itself is a non-atomic read-then-write (benign: every replica writes the same value).
Likely follow-up
"What if the probe is a greeting that never touches the database?" — it still closes the breaker; a better probe would exercise the failing dependency.
Q27. Is the breaker's 10-second window a true sliding window?CurveballReliability
Direct answer
No. The failure and total counters get their 10 s TTL refreshed on every recorded outcome, so under continuous traffic they never expire. The ratio becomes cumulative since the last quiet 10 s gap; after hours of successes, a sudden outage needs many failures before the ratio reaches 50 %.
Explanation
A true window would bucket counts by time (e.g. per-second keys summed over 10 s) or use a sorted set like the rate limiter.
Evidence
voxa-backend/app/circuit_breaker.py:87–98 (the class docstring also says "refreshed on every recorded outcome")
Trade-off / limitation
Simpler code vs slower trip under sustained load.
Likely follow-up
"Write the fix" — an atomic Lua script: INCR per-second bucket keys with 11 s TTL, sum the last 10.

Q36. What is HNSW and why pgvector?IntermediateAI / ML
Direct answer
HNSW is a multi-layer proximity graph for approximate nearest-neighbour search: start at a sparse top layer, greedily move to closer nodes, descend layers. pgvector adds vector types, distance operators and HNSW/IVFFlat indexes to PostgreSQL, so vectors sit next to relational data.
Explanation
vector_cosine_ops matches the <=> cosine-distance operator used in the query.
Evidence
voxa-backend/app/database.py:58–63, voxa-backend/app/rag_engine.py:68–75

Likely follow-up
"IVFFlat vs HNSW?" — IVFFlat clusters vectors and needs training data; HNSW has better recall/speed but slower builds and more memory.

4. Scaling and failure scenarios

Capacity estimate (assumptions stated, not measurements)

Assume a peak of 5,000 concurrent chat users, each sending one message every 30 s.

  • Message rate: 5,000 / 30 ≈ 167 messages/s.
  • Database writes: 2 message rows per turn → ≈ 333 inserts/s (plus conversations on first turns).
  • Storage: assume ~500 bytes per message row → 333 × 500 B ≈ 167 KB/s ≈ 14 GB/day if peak lasted all day; real daily volume would be far lower.
  • Embeddings: if 40 % are generic questions and half of those miss the cache → 167 × 0.4 × 0.5 ≈ 33 misses/s × 3 embeddings ≈ 100 embeddings/s. Measure the per-embedding CPU time; at an assumed 10 ms that is ~1 CPU core of embedding work.
  • Redis: roughly 8 commands per message (rate limit, breaker read/write, cache SCAN/MGET, counters) → ≈ 1,300 commands/s, well within one Redis instance.
  • Hidden limit: every open WebSocket subscribes to its own Pub/Sub channel, and redis-py holds one Redis connection per subscription (voxa-backend/app/main.py:471). 5,000 sockets ≈ 5,000 Redis connections; Redis's default maxclients is 10,000. Fix: one shared subscription per gateway (pattern subscribe or a dispatcher keyed by session).
Scenario 1 — Traffic grows 10×

Impact: gateway CPU (embeddings), Redis connections (one per socket), Postgres connections and insert rate. Solutions: more gateway replicas behind a load balancer; shared Pub/Sub dispatcher; PgBouncer; batch message inserts; embed once per request. Trade-off: more infrastructure. Test: k6 at 1×, 2×, 5×, 10× with a realistic question mix, watching p95 and error frames.

Scenario 2 — The LLM worker dies mid-task

Impact: SSE requests wait; entries stay pending. Today: supervisor reclaims after 15 s; SSE times out at 20 s with a fallback and breaker failure. Improve: run ≥ 2 workers; shorter idle threshold with ownership renewal. Test: kill the container during an E2E request and assert the answer or fallback arrives.

Scenario 3 — Slow database queries

Impact: router exceptions or timeouts feed the breaker; WebSocket answers slow. Improve: statement timeouts, indexes (orders by user), read replica for admin metrics, replace all-time percentile_cont with Prometheus histograms. Test: inject latency with pg_sleep in a test environment.

Scenario 4 — Duplicate requests

Impact: double tickets (at-least-once delivery or client retries). Today: optional idempotency key returns 409. Improve: store and replay responses; unique constraint on ticket trace_id. Test: send the same request twice concurrently; assert one ticket.

Scenario 5 — Redis unavailable

Impact today: WebSocket sessions close (unguarded breaker read), REST returns 500, workers stall. Improve: managed Redis with replica failover; guard every Redis call with explicit fail-open/closed decisions; local in-memory breaker fallback. Test: stop Redis during a run.

Scenario 6 — Knowledge base grows to 1 million passages

Impact: HNSW build time and memory; recall vs speed tuning; storage ≈ 1M × 384 × 4 B ≈ 1.5 GB of raw vectors before index overhead. Improve: tune ef_search, filter by topic/product first, consider a dedicated vector store if Postgres resources are contended. Test: recall@k against exact search on a sample.

Scenario 7 — edge-tts or Hugging Face is unreachable

Impact: no voice audio (text still works); fresh containers cannot download models and the STT worker crashes on start. Improve: bake models into images or a mounted volume; supported TTS API; health checks that report degraded mode.

Existing vs proposed
Voxa implements this minus load balancer, HA and HTTPS.
SD2. Add voice in and voice out with under-2-second response for short questions.
Approach
Streaming STT with voice activity detection, streaming TTS, overlap stages (start TTS on first sentence).
Voxa today
Whole-utterance STT → full answer → full MP3; sequential stages.
Proposal
MediaRecorder chunks over WebSocket, partial transcripts, sentence-level TTS chunks, measure each stage with trace IDs.
Risks
CPU cost, barge-in handling, network jitter.
SD3. Design a distributed rate limiter.
Options
Fixed window (INCR + EXPIRE), sliding log (Voxa: sorted set + Lua), sliding window counter, token bucket.
Choice
Atomic in Redis so all replicas share one budget; key by user, fall back to IP.
Failure
Decide fail-open (availability) vs fail-closed (protection) per endpoint.
Scale
Shard keys across Redis Cluster; local pre-filter for abusive IPs.
SD4. Make the answer cache work for millions of entries.
Problem
Linear scan of a 50-key sample does not scale.
Design
Vector index (Redis vector search or pgvector table) with k-NN query, threshold on the best match, TTL and versioned namespace, store only generic answers.
Trade-offs
Index memory, recall, staleness, cache poisoning risk.
SD5. Move the Azure deployment to high availability.
Design
Two+ gateway instances across availability zones behind a TLS load balancer; managed Postgres (zone-redundant) and managed Redis with replica; workers as autoscaled containers; images in a registry built by CI; secrets in a vault.
Trade-offs
Cost and complexity vs uptime; WebSocket draining during deploys.
Existing vs proposed
Today: one VM, Compose, no TLS — all of this is proposed.

Glossary

TermMeaning
ASGIAsynchronous Server Gateway Interface — the standard between Python async servers (Uvicorn) and frameworks (FastAPI).
At-least-once deliveryEvery task is processed one or more times; never silently lost, possibly duplicated.
Circuit breakerA switch that stops calls to a failing dependency for a cooldown, then tests with one probe.
Consumer groupRedis Streams feature that splits a stream's entries among several consumers and tracks acknowledgements.
CORSCross-Origin Resource Sharing — browser rule deciding which websites may call an API.
Cosine similarityHow closely two vectors point in the same direction (1 = same, 0 = unrelated).
DLQDead-letter queue — where tasks go after too many failures, for inspection.
EmbeddingA vector of numbers representing the meaning of text.
Event loopThe scheduler inside asyncio that switches between waiting tasks on one thread.
HNSWHierarchical Navigable Small World — graph index for fast approximate nearest-neighbour search.
HPAHorizontal Pod Autoscaler — Kubernetes object that changes replica counts from metrics.
IaaS / PaaSInfrastructure / Platform as a Service — you manage the OS (VM) vs the provider manages it.
IdempotencyDoing an operation twice has the same effect as doing it once.
INT8 quantisationStoring model weights as 8-bit integers to save memory and speed up inference.
JWTJSON Web Token — signed token carrying user claims such as ID, role and expiry.
Lua script (Redis)Small program Redis runs atomically, without interleaving other commands.
NSGAzure Network Security Group — firewall rules for a VM's network interface or subnet.
PELPending Entries List — per consumer group list of delivered but unacknowledged stream entries.
PIIPersonally identifiable information — card numbers, phone numbers, SSNs and similar.
Pub/SubPublish/subscribe messaging: publishers send to a channel; current subscribers receive it.
p9595th percentile — 95 % of values are at or below it.
RAGRetrieval-augmented generation — retrieve documents, then have a language model generate an answer from them. Voxa implements only the retrieval part.
Secure contextA page served over HTTPS (or from localhost); required for microphone, clipboard and some crypto APIs.
SSEServer-Sent Events — one-way server-to-browser event stream over HTTP.
TTFTTime to first token — delay before the first piece of an answer arrives.
