Layer 1 — Project at a Glance

What Voxa is, what it really does today, how to run it, and how to explain it honestly.

1. Purpose, problem, users

👶 Beginner Intuition (ELI5): Why do companies build customer support bots? Because hiring 100 human agents costs millions of dollars per year, and 70% of customer questions are identical: "Where is my package?" or "How do I return this?". Voxa is an automated assistant designed to answer these routine questions instantly (under 500 milliseconds), look up database records, issue refunds safely, and hand off difficult problems to human agents.

The Project at a Glance

Voxa (“Voxa 2.0”, app.title in voxa-backend/app/main.py:78-83) is a customer-support platform for a fictional consumer hardware brand (AuraSound Earbuds, StudioPro Headphones, Clarity 4K Webcam). Users interact via text chat or browser speech. The backend checks order status, calculates refund eligibility, retrieves company policy text, and opens support tickets.

The Real-World Business Problem

E-commerce stores face three massive customer service challenges:

  • Abandonment from slow answers: If a customer waits >60 seconds for an answer, cart abandonment jumps by 40%.
  • Repetitive volume fatigue: Human support agents spend 65-75% of their day answering repetitive status queries rather than resolving difficult issues.
  • Financial risk of hallucinations: A generative AI model might accidentally say "Sure, I refunded your $200 order!" when policy forbids it. Voxa prevents this by using deterministic database tools for financial operations.

The 3 Target Personas

  • Alice (The Impatient Customer): Wants an instant status on her order ORD-88412 while waiting in line at a coffee shop on mobile. Wants zero delays and crystal-clear answers.
  • Bob (The Human Tier-2 Agent): Receives escalated cases when a customer is angry or has a complex defective product issue. Needs full conversation history and an automated support ticket.
  • Carol (The SRE / Store Admin): Monitors latency (p95/p99), server uptime, Redis memory consumption, and API error rates on Prometheus dashboards (prometheus.yml).

Core Technical Constraints

Customer support systems must guarantee low latency (<500ms TTFT), high availability, and financial correctness. A refund cannot be processed twice (requires idempotency), orders cannot be viewed by unauthorized strangers (requires access control), and common queries must not overload backend databases (requires semantic caching).

Beginner's Rosetta Stone: 12 Foundational Concepts Decoded with Everyday Analogies

If you have zero background in distributed systems, memorize these 12 intuitive mental models. Every MAANG interview question boils down to one of these principles:

1. Client-Server & WebSockets

Analogy: HTTP is like sending postal letters (you send a request, wait, and get a reply; the connection closes). A WebSocket is like a live telephone phone call: you pick up once, keep the line open, and both sides can talk back and forth at any microsecond without redialing.

In Voxa: Used in chat/page.tsx:94 and main.py:277 (/v1/ws/stream) to stream word-by-word responses to the user.

2. FastAPI & Async Concurrency

Analogy: A synchronous server is like a waiter who takes your order to the kitchen, stands there watching the chef cook for 10 minutes, and ignores all other tables. An Async server takes your order, tells the kitchen, and immediately serves 50 other tables while your food is cooking.

👶 What physically happens on await? Python doesn't pause the CPU. It registers the network socket with the operating system kernel (using epoll on Linux or kqueue on macOS) saying "wake me when bytes arrive" and yields control back to the single-threaded event loop. The CPU immediately executes work for other users. When the database or Redis returns data, the OS signals the event loop to resume execution right where it left off!

In Voxa: Built with Python 3.11 async/await and Uvicorn (main.py:78) to handle thousands of concurrent customer connections on a single thread.

3. PostgreSQL 16 vs Redis

Analogy: PostgreSQL is a heavy steel bank vault with permanent paper ledgers on disk (never loses data even if power dies, ACID-compliant). Redis is a digital whiteboard in RAM right above your desk (lightning fast, reads take microseconds, but memory is expensive and volatile).

In Voxa: Postgres stores orders, tickets, and policy documents (models.py). Redis stores cache entries, rate limit tokens, and circuit breaker status (rag_engine.py).

4. Vector Embeddings (384-D GPS)

Analogy: Turning a sentence into 384 numbers is like assigning it a GPS latitude and longitude of meaning. "Where is my sneaker parcel?" and "Track my shoe order" use totally different words, but land on almost the exact same coordinate on the globe of concepts.

In Voxa: The local sentence-transformers/all-MiniLM-L6-v2 neural network converts text into 384 floating-point numbers (rag_engine.py:35).

5. Cosine Similarity

Analogy: Imagine standing in the center of a dark room with two laser pointers. One pointer aims at Sentence A, one aims at Sentence B. Cosine similarity measures the angle between the two beams. If the angle is 0° (cosine = 1.0), they point in the exact same direction. If 90°, they are completely unrelated.

In Voxa: Postgres calculates cosine distance using the <=> operator in pgvector (rag_engine.py:101).

6. Semantic Cache vs Exact Cache

Analogy: An exact-match cache is like a strict schoolmaster: if you ask "What is the return policy?" and someone else asks "What is the return policy?", it matches; but if you add an exclamation mark ("What is the return policy?!"), it fails. A Semantic Cache understands that both questions mean the same thing and returns the saved answer instantly.

In Voxa: Stored in Redis under semcache:* with a 0.92 cosine similarity threshold (rag_engine.py:183).

7. Deterministic Router vs LLM

Analogy: An LLM (Large Language Model) is like a creative student: brilliant, but occasionally makes up facts (hallucinates) and costs money per word. A Deterministic Router is like a vending machine with mechanical gears: press B4, and a soda drops every single time with 100% predictability, 0ms thinking time, and $0 cost.

In Voxa: The 13-branch router in main.py:339-419 handles orders, refunds, and tickets deterministically for safety and speed.

8. Token Bucket Rate Limiting

Analogy: A coffee dispenser that drips 10 drops of water per minute into a small cup. Whenever you click a button, you drink 1 drop. If you click 5 times fast, you drink 5 drops (burst allowed). But once the cup is dry, you must wait for the drip. You cannot flood the system.

In Voxa: Implemented using a custom Redis Lua script in main.py:165-176 to prevent race conditions during high traffic.

9. Circuit Breaker Pattern

Analogy: The electrical fuse box in your home. If a broken toaster in the kitchen starts short-circuiting, the fuse trips OPEN so your whole house doesn't catch fire. Once the issue is resolved, it goes HALF-OPEN to test with a small current, then resets to CLOSED.

In Voxa: Implemented in circuit_breaker.py to stop hammering downstream AI models or databases if they fail or time out.

10. Idempotency Keys

Analogy: The elevator call button. If you are in a rush and press the "Floor 5" button 10 times in 3 seconds, the elevator doesn't dispatch 10 separate elevators; it recognizes the intent has already been registered and performs the action once.

In Voxa: Stored in Redis via SET NX EX in agent_tools.py:140 so a customer double-clicking "Refund" is only refunded once.

11. Redis Streams vs Pub/Sub

Analogy: Pub/Sub is like a live FM radio station: if your car radio is turned off when a song plays, you miss it forever. Redis Streams is like an unread WhatsApp group chat: messages are saved in an append-only log on disk, given unique IDs, and wait until a worker confirms with an XACK (read receipt).

In Voxa: Streams queue audio chunks (stream:audio:transcribe) and inference jobs (stream:llm:inference) in queue_manager.py:21.

12. Insecure Direct Object Reference (IDOR)

Analogy: A hotel where your electronic keycard has your room number printed on the back. If you take a sharpie, write another room's number over it, and the door lock opens without checking if you rented that room, that is an IDOR vulnerability.

In Voxa: Endpoint /v1/tools/order/{order_id} returns full order details for any order ID passed in the URL without checking if the logged-in user owns it.

Step-by-Step Visual Timeline of a User Query

Here is what happens inside Voxa in the 80 milliseconds after Alice types "Where is order ORD-88412?":

  1. WebSocket Packet Arrival (t = 0ms): The browser sends a JSON frame {"type":"text_query","text":"Where is order ORD-88412?"} over the established WebSocket (main.py:306).
  2. Rate Limiter Check (t = 1ms): Redis runs a Lua script to check Alice's IP/token against the token bucket. If within limit, request proceeds; if exceeding, returns 429.
  3. Circuit Breaker Inspection (t = 2ms): Gateway checks Redis key circuit:ai_worker:state. It is CLOSED (healthy), so execution continues.
  4. Semantic Cache Scan (t = 8ms): Gateway encodes the sentence into a 384-d vector and scans Redis semcache:* keys. If an earlier identical query exists with cosine similarity ≥ 0.92, the cached answer is streamed immediately.
  5. Deterministic Intent Router (t = 10ms): On a cache miss, the regex pattern ORD-\d{5} matches ORD-88412 (main.py:356). The router picks the SQL Order Lookup tool.
  6. Database Query (t = 18ms): Async SQLAlchemy issues SELECT * FROM orders WHERE order_id = 'ORD-88412' to PostgreSQL 16 (agent_tools.py:75). The record is returned: Status = "Shipped", Carrier = "FedEx".
  7. Response Synthesis & Cache Store (t = 20ms): The gateway constructs the answer string and saves it into Redis under semcache:{hash} with a 3600-second TTL.
  8. Token Chunk Streaming (t = 22ms - 80ms): The gateway loops over words, sending {"type":"token_chunk","token":"Your order ORD-88412..."} every 30ms to create a natural typing animation on Alice's screen (main.py:425).

2-Minute Technical Walkthrough (The SDE-1 Depth Answer)

“I built Voxa to solve the latency and hallucination problems common in AI customer support. The architecture consists of three core layers:

  • The Client Layer: A Next.js 14 frontend with a real-time telemetry HUD that displays Time-to-First-Token (TTFT) and end-to-end latency. It supports both text and voice input using the browser's native Web Speech API.
  • The Gateway Layer: An asynchronous FastAPI backend. When a message arrives at /v1/ws/stream, it runs through a token-bucket rate limiter implemented as an atomic Redis Lua script, and checks a circuit breaker to prevent cascading failures. It then generates a 384-dimensional dense embedding using a local all-MiniLM-L6-v2 model. If an existing query in the Redis semantic cache has a cosine similarity above 0.92, it immediately streams the cached response.
  • The Data & Tool Layer: On a cache miss, rather than blindly forwarding the query to an expensive, unpredictable LLM, the system uses a deterministic intent router. If the user provides an order ID like ORD-88412, it executes an async SQLAlchemy query against PostgreSQL 16. If they request a refund, it checks whether the order was delivered within 30 days and performs an ACID transaction. For policy questions, it uses pgvector's cosine distance operator to retrieve the top matching clause from seeded warranty and shipping documents.
  • Architectural Honesty: While the codebase includes scaffolding for decoupled Redis Streams workers—including a faster-whisper STT worker and an LLM worker—the main gateway operates as a fast, self-contained synchronous service because customer support queries require sub-100ms deterministic guarantees.”
5-Minute Senior Architectural Defense (MAANG Staff/Lead Level)

Use this version when an interviewer asks: "Walk me through the system design, your biggest technical challenges, and what you would do differently in production."

Part 1: The Core Design Philosophy
“When designing Voxa, my primary objective was deterministic correctness for financial transactions combined with sub-second responsiveness. In e-commerce customer support, you cannot afford probabilistic hallucination when dealing with money. If a user asks for a refund, an LLM might promise money that policy forbids. Therefore, I architected the gateway to strictly decouple deterministic transactional tools (orders, refunds, ticket creation) from semantic text retrieval (policy RAG).”

Part 2: The Two Most Interesting Engineering Trade-offs
“First, the Semantic Cache. A standard key-value cache uses exact string matching, which has an almost 0% hit rate in conversational chat because users phrase questions differently ('Where is ORD-123?' vs 'Status of ORD-123 please'). By caching 384-dimensional vectors in Redis and calculating cosine similarity, we achieve cache hits across paraphrased intents. However, in my current implementation, the gateway scans keys using KEYS semcache:*, which is an $O(N)$ blocking command. In production with 100,000 cached entries, this would stall the single-threaded Redis event loop. My planned migration is to store vectors in Redis HNSW indexes (RediSearch) or pgvector HNSW to achieve $O(\log N)$ logarithmic vector search.

Second, the Worker Pipeline Decoupling. I set up Redis Streams (stream:audio:transcribe and stream:llm:inference) with consumer groups for speech-to-text and language modeling. In testing, I found that the gateway published audio chunks to the stream, and the Whisper worker transcribed them and pushed tokens to Redis Pub/Sub, but the gateway lacked an active Pub/Sub subscriber listener to relay those tokens back to the WebSocket client. Identifying this decoupling taught me the critical difference between building independent worker scaffolding and managing end-to-end backpressure across distributed message buses.”

Part 3: Security & Production Hardening
“From a security standpoint, the current codebase has two key areas for hardening: the tool endpoint /v1/tools/order/{id} has an IDOR vulnerability because it doesn't verify whether the requesting user owns that order, and the WebSocket endpoint currently accepts unauthenticated connections. In my production design, the WebSocket handshake requires a validated Bearer JWT, and all database queries enforce row-level security: WHERE order_id = :id AND user_id = :current_user.”

Technology Intuition Cards: Why These Exact Tools?

FastAPI vs Flask / Django

Why chosen: Django is too heavy and traditionally synchronous. Flask lacks native async WebSocket handling. FastAPI is built natively on top of Starlette (high-performance async ASGI) and Pydantic (type safety). It allows 1 single Python process to maintain thousands of idle WebSocket connections waiting on user keypresses without consuming 1 OS thread per user.

PostgreSQL + pgvector vs Dedicated Vector DB

Why chosen: Why not use Pinecone, Milvus, or Qdrant? Because in customer support, you need to link a policy document with transactional data (like user permissions, orders, and tickets). If you use a separate vector DB, you suffer from the Dual-Write Problem: what if a write to Postgres succeeds but the write to Pinecone fails? With pgvector, your relational data and your vector embeddings live in the exact same database engine under the same ACID transaction!

Redis 7 vs Memcached

Why chosen: Memcached is a simple string key-value store with no persistence and no advanced data structures. Redis supports Sorted Sets (ZSETs) for sliding-window rate limiters, Lua scripts for atomic execution, Pub/Sub for streaming events, and Streams for durable worker message logs.

Local MiniLM vs OpenAI Embeddings API

Why chosen: Calling OpenAI's text-embedding-3-small API adds 80-150ms of network latency per message and costs money for every user query. The local all-MiniLM-L6-v2 model is only 80MB, runs directly on server CPU in 12-18ms, has zero API cost, and never leaks private customer conversations to a third party.

5. High-level architecture (as implemented)

A gateway is the front desk host. Heavy or slow background tasks (transcribing audio files) are dropped onto a message queue so the front desk never freezes. Background workers pick jobs off the queue when ready.
In the actual codebase, the WebSocket text path and REST endpoints are 100% complete end-to-end. The audio streaming worker pipeline (audio_chunk → stream:audio:transcribe → STT → stream:llm:inference → LLM worker → Pub/Sub) stops at Pub/Sub because the gateway has no active subscriber thread.
To wire the worker pipeline in production: in the WebSocket handler, spin up an async task asyncio.create_task(listen_pubsub(session_id)) using redis.pubsub() to read from channel token:stream:{session_id} and forward token chunks directly to the client socket.

7. The Recipe & Rulebook (pgvector RAG)

8. The Prep Line Cooks (Background Workers)

FastAPI + asyncio (The Gateway)

👶 ELI5 Analogy: A synchronous server is like a post office clerk who serves one customer, walks all the way to the back room to find their parcel, waits 5 minutes, and makes the line of 50 people wait outside. FastAPI + asyncio is a smart clerk who hands the warehouse request to a conveyor belt and immediately serves the next person in line while the parcel is traveling!

A high-speed Python web framework. Async code lets one single Python process juggle thousands of idle network connections without dedicating an expensive OS thread to each. When Python executes await, it hands a callback file descriptor to the OS kernel (via epoll on Linux or kqueue on macOS) and returns to the event loop to serve other users. When the socket receives bytes, the kernel notifies the event loop, which seamlessly resumes execution.
Instantiated via app = FastAPI(lifespan=...) (main.py:78). Uses Depends() for DB sessions and auth, Pydantic v2 models for strict type validation, and @app.websocket('/v1/ws/stream') for duplex chat. Failure mode: Any blocking CPU call inside an async def route stalls all other users on that worker process—e.g. self.encoder.encode() runs synchronously in rag_engine.py:35.
Fix CPU blocking by offloading encoding to an async threadpool: await asyncio.to_thread(self.encoder.encode, text) or deploying a dedicated Triton / TorchServe embedding microservice. In production, Uvicorn runs with 2 workers (Dockerfile.gateway:23).
WebSocket + SSE (Real-Time Communication)

👶 ELI5 Analogy: Standard HTTP is like sending a postcard: you write a message, mail it, and wait for a postcard back. A WebSocket is like picking up a telephone: once the call connects, both people can talk and listen at the exact same time with zero setup delay.

WebSockets maintain a long-lived, bidirectional, full-duplex TCP socket between browser and server. Server-Sent Events (SSE) is a unidirectional stream where the server pushes events to the browser over standard HTTP.
In Voxa, the chat console connects to ws://.../v1/ws/stream (main.py:277). The gateway runs an infinite loop await websocket.receive_text(), parses JSON, and emits token chunks. Failure mode: There is no try/except around json.loads(); malformed JSON immediately raises an unhandled exception and abruptly closes the socket.
Scaling WebSockets horizontally across multiple server instances requires a shared backplane (Redis Pub/Sub or AWS API Gateway WebSocket management) because a client connected to Server A cannot receive messages pushed to Server B without a message bus.
Redis 7 (Cache, Limiter, Breaker, Streams)

👶 ELI5 Analogy: Your computer's hard drive is like a book in a library (takes seconds to walk over and open). Redis is like a sticky note pasted on your forehead (reads take microseconds because it lives directly in RAM memory).

An open-source, in-memory data store with sub-millisecond response times. Used as a high-speed cache, an atomic rate limiter, and an append-only event stream.
Voxa uses Redis for 5 distinct tasks: (1) semcache:* vector cache, (2) ratelimit:* sorted sets via Lua script, (3) idempotency:* via SET NX EX, (4) circuit:* state flags, and (5) Redis Streams (stream:audio:transcribe) in queue_manager.py:21.
Redis Streams provide at-least-once delivery with consumer groups and acknowledgments (XACK). Compare: Kafka is designed for multi-gigabyte persistent log streams; Redis Streams is lightweight, in-memory, and perfect for real-time microservices.
PostgreSQL 16 + pgvector (Relational & Vector Data)

👶 ELI5 Analogy: Traditional SQL databases only understand exact numbers and words (e.g. WHERE price = 99). The pgvector extension gives Postgres artificial eyes: it can measure the meaning of sentences and find the closest match even if the words are completely different.

PostgreSQL is the world's most advanced open-source relational database. The pgvector extension adds native support for vector columns and similarity search operators like cosine distance (<=>).
Schema in models.py defines relational tables (orders, support_tickets, users) and a knowledge_base table with a Vector(384) column. Seeded with 5 policy documents in seed_db.py. Gaps: No HNSW or IVFFlat index is created on the vector column; at 5 rows it runs an exact sequential scan, which will degrade to $O(N)$ at scale.

E. AI, RAG and pipelines

👶 Vector Embeddings & RAG Explained from Absolute Zero: What is a vector? It's simply an array of 384 floating-point numbers (e.g. [0.14, -0.82, 0.45, ...]). Think of each number as a slider on a giant mixing board: one slider measures "refund urgency", another measures "hardware topic", another measures "sentiment". Similar sentences end up with almost identical slider values! RAG (Retrieval-Augmented Generation) means taking the user's question, finding the closest policy slider values in PostgreSQL, and using that exact text to answer.

The Math of Cosine Similarity Made Simple

How does the database measure how close two sentences are? It calculates the Cosine Similarity between their 384-dimensional vectors:

Similarity = (A · B) / (||A|| × ||B||)

  • Similarity = 1.0 (Angle = 0°): The sentences mean the exact same thing (e.g., "Where is my package?" vs "Where is my package?").
  • Similarity = 0.94 (Angle ≈ 20°): The sentences are paraphrased (e.g., "Where is my order?" vs "Track my delivery status"). Matches the semantic cache threshold (≥ 0.92)!
  • Similarity = 0.15 (Angle ≈ 80°): The sentences are completely unrelated (e.g., "Where is my shoe?" vs "What is the airspeed of a swallow?").

The pgvector <=> Operator: In PostgreSQL pgvector, <=> computes Cosine Distance, which is defined as: Distance = 1 - Similarity. Therefore, a distance of 0.0 means identical, and a distance < 0.65 corresponds to a similarity > 0.35 (rag_engine.py:101).

H. Testing, security, reliability, performance

The 3 Critical Security Vulnerabilities Explained as Real-World Hacker Stories

1. The IDOR Vulnerability (Insecure Direct Object Reference)

The Hacker Story: Attacker Eve buys a $15 replacement cable and gets order ORD-10001. She notices the URL endpoint /v1/tools/order/ORD-10001 returns her receipt. She writes a Python loop incrementing the number: ORD-10002, ORD-10003... The server gladly hands over Alice's home address, full name, and purchased items! The code in agent_tools.py:75 runs SELECT * FROM orders WHERE order_id = :id without checking if Eve actually owns that order.

The 3-Line MAANG Fix: Require user authentication on the route and enforce tenant isolation: 

user = Depends(get_current_user)
query = select(Order).where(Order.order_id == id, Order.user_id == user.id)

2. The Unverified JWT Signature Bypass

The Hacker Story: In auth.py:52-60, the code attempts to import jose. If the library fails or encounters an import issue, it falls back to decoding claims without cryptographic signature verification! Eve generates a forged JWT containing {"sub": "eve", "role": "admin"} signed with an arbitrary bogus key. The server parses the JSON payload and grants Eve complete administrative privileges.

The 3-Line MAANG Fix: Never implement permissive fallbacks in authentication code. Fail closed: 

if not JOSE_AVAILABLE:
    raise RuntimeError("Cryptographic library missing; refusing to start")
payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])

3. The Open, Unauthenticated WebSocket

The Hacker Story: The WebSocket endpoint main.py:277 (/v1/ws/stream) calls await websocket.accept() immediately without checking any cookie, authorization header, or session token. Eve writes a script opening 20,000 simultaneous WebSockets, sending random queries. Each query triggers in-process BERT embeddings and Redis KEYS scans, exhausting server file descriptors and CPU.

The 3-Line MAANG Fix: Authenticate during the initial HTTP 101 WebSocket handshake: 

token = websocket.query_params.get("token")
if not verify_token(token):
    await websocket.close(code=status.WS_1008_POLICY_VIOLATION)

Reliability Patterns Implemented in Voxa

  • Atomic Token Bucket Rate Limiting: Implemented via a Redis Lua script in main.py:165-176. Because Redis runs Lua scripts as a single atomic operation, two requests arriving at the exact same microsecond cannot trigger a race condition or bypass the 60 requests/minute limit.
  • Circuit Breaker Pattern: In circuit_breaker.py, tracking consecutive failures against Redis key circuit:ai_worker:state. If downstream AI workers or databases fail 5 consecutive times, the circuit trips to OPEN and immediately returns a polite fallback message to users without waiting for timeouts.
  • ACID Database Transactions: In agent_tools.py:146, refund processing wraps order status mutations inside async with session.begin():. If an error occurs midway through processing, the entire transaction rolls back automatically, preventing orphaned money states.

2. "Your semantic cache scans all keys with KEYS semcache:*. Won't that freeze Redis in production?"

🗣️ Word-for-Word Verbal Script:
“Yes, you are 100% right. In my current prototype, the cache uses KEYS semcache:* in rag_engine.py:165, which performs an $O(N)$ full keyspace scan. 3. "What happens if a user clicks 'Refund' on two different browser tabs at the exact same millisecond?"

🗣️ Word-for-Word Verbal Script:
“This is a classic race condition known as a double-refund attack. Voxa handles this at two independent layers: First, at the application layer using Redis distributed idempotency keys: before processing, the tool executes SET idempotency:refund:{order_id} 'pending' NX EX 86400. If a second request arrives with the same order ID, the NX (Not Exists) condition fails and immediately rejects the second request. Second, at the database layer, we wrap the status mutation inside an ACID transaction with row-level locking: SELECT * FROM orders WHERE order_id = :id FOR UPDATE. The first transaction acquires the exclusive row lock and flips the status to 'Refunded'; the second transaction waits for the lock, reads the updated status, and terminates with 'Already Refunded'.”

4. "Why did you use WebSockets instead of simple HTTP REST or Server-Sent Events (SSE)?"

🗣️ Word-for-Word Verbal Script:
“I chose WebSockets because customer support chat is inherently bidirectional and latency-sensitive. While SSE is great for server-to-client streaming, it is strictly one-way; if the user wants to interrupt the assistant mid-stream or send audio voice chunks, they must open separate HTTP POST connections. A WebSocket maintains a single, persistent, full-duplex TCP connection, allowing simultaneous audio streaming upstream and token chunks downstream with zero per-message handshake overhead.”

📐 SDE-1 Back-of-the-Envelope Mental Math & Sizing Pocket Guide (MAANG 2026)

🎯 The Rule of Mental Math in MAANG System Design: Interviewers do not expect exact decimals—they test whether you know standard order-of-magnitude estimates and can convert QPS into daily volume, RAM storage, and bandwidth in your head under pressure.

1. The 100K Daily Request Constant

One second has 86,400 seconds. In system design, round 86,400 up to 100,000 (10⁵) for fast mental math:

  • 1 QPS ≈ 86,400 req/day ≈ 100,000 requests/day
  • 10 QPS ≈ 864,000 req/day ≈ 1 million requests/day
  • 100 QPS ≈ 8.64 million req/day ≈ 10 million requests/day
  • 1,000 QPS ≈ 86.4 million req/day ≈ 100 million requests/day
  • Peak Factor: Average QPS × 2 to 3 = Peak Traffic QPS (e.g. 100 avg QPS → 300 peak QPS).

2. Vector Embedding RAM Sizing Formula

How much RAM does a vector database or Redis cache need for 384-dimensional embeddings?

  • Each vector element is a 32-bit float: 4 bytes.
  • Size per vector: 384 × 4 bytes = 1,536 bytes ≈ 1.5 KB per vector.
  • For 10,000 vectors: 10,000 × 1.5 KB = 15 MB.
  • For 100,000 vectors: 100,000 × 1.5 KB = 150 MB.
  • For 1,000,000 vectors: 1,000,000 × 1.5 KB = 1.5 GB.
  • Takeaway: 1 million policy chunks easily fit inside a single $15/month Redis instance with 4GB RAM!

3. Bandwidth & Network Ingestion

How much network bandwidth does Voxa consume at 100 QPS?

  • Average user JSON frame: {"type":"text_query","text":"..."} ≈ 500 bytes (0.5 KB).
  • At 100 QPS: 100 × 0.5 KB = 50 KB/sec = 400 Kbps (negligible).
  • 10,000 Idle WebSockets: Sending a 64-byte heartbeat ping every 30 seconds:
    10,000 / 30 ≈ 333 pings/sec × 64 bytes ≈ 21 KB/sec.
    Takeaway: Network bandwidth is rarely the bottleneck for chat; connection concurrency and memory are.
