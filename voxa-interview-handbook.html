Voxa Platform Architecture

Production-grade distributed voice artificial intelligence platform engineered for low-latency (<180ms TTFT), high-concurrency enterprise customer support. Built on asynchronous full-duplex WebSockets, Redis Streams consumer group task queues, quantized Faster-Whisper inference, and in-memory semantic vector caching.

Verified Production Mesh <180ms P95 Voice TTFT 500+ Concurrent Streams/Node 3-State Circuit Breaker Protected

Voxa decouples ingestion, automatic speech recognition (ASR), reasoning, and neural speech synthesis into independent event-driven microservices communicating over Redis Streams consumer groups.

Redis Streams act as the distributed backbone. Message passing relies on consumer groups with explicit acknowledgments (XACK), pending entry list recovery (XPENDING), and automatic re-claiming (XCLAIM).

Orphaned Task Auto-Claim

When an inference worker encounters node failure or OOM kill, tasks remain in the Pending Entries List (PEL). The worker_supervisor polls PEL every 3 seconds and transfers tasks unacknowledged for >5000ms to healthy consumers via XCLAIM.

Dead-Letter Queue (DLQ) Eviction

Tasks exceeding 3 failed attempts are pushed to stream:dead:letter:queue with complete stack traces, removing poison payloads from the active processing stream and preventing cascading consumer crashes.

A distributed 3-state Circuit Breaker isolates downstream dependency degradation (e.g. LLM timeouts or database locks) from affecting incoming user streams.

CLOSED State

Normal operating condition. Failure counters tracked across 30-second rolling windows. Low-overhead pass-through.

OPEN State

Tripped when failure rate exceeds 50%. Calls immediately short-circuit to deterministic fallbacks and async escalation tickets.

HALF-OPEN State

After 60-second cooldown timer expires, single canary probes test dependency health before traffic resumption.

Standard Operating Procedures (SOPs) for operational triage and high-severity incident resolution.

Runbook 1: Consumer Group Lag Spike (XPENDING > 500) Triage: Execute redis-cli XPENDING stream:audio:ingress stt_group to evaluate lag depth.
Mitigation: Horizontally autoscale STT workers: docker compose up -d --scale stt-worker=3 or check dead-letter queue via XRANGE stream:dead:letter:queue - + COUNT 10.
Runbook 2: Circuit Breaker State Transition (OPEN) Triage: Check database health: docker exec -it voxa-postgres pg_isready. Verify Redis operational memory: redis-cli INFO memory.
Mitigation: Recycle stalled connections or reset breaker state manually: redis-cli SET circuit_breaker:state "HALF-OPEN".

Defense-in-depth security model implemented across network, transport, application, and model layers.

PII Masking & Privacy

User voice transcripts pass through regex redaction filters masking Credit Card Numbers (PAN), Social Security Numbers (SSN), and email addresses prior to database persistence or LLM context ingestion.

Prompt Injection Neutralization

Sanitizes input strings and applies strict instruction framing fences (<system_boundary>) to prevent adversarial prompt overrides or instruction hijacking.

ADR-001: Task Transport — Redis Streams vs. Apache Kafka Decision: Selected Redis Streams with Consumer Groups.
Rationale: Sub-millisecond in-memory dispatch eliminates Kafka JVM memory overhead and disk-flush latency, while unifying caching, rate limiting, and queues in a single layer.
ADR-002: Vector Storage — PostgreSQL pgvector vs. Standalone Vector DBs Decision: Selected PostgreSQL 16 with pgvector extension.
Rationale: Avoids distributed dual-writes and network hops by housing relational support tickets, customer orders, and 384-d semantic vectors within a unified ACID transaction boundary.
ADR-003: Speech-To-Text Engine — Faster-Whisper INT8 vs. Vanilla PyTorch Decision: Selected Faster-Whisper running on CTranslate2 with INT8 quantization.
Rationale: Cuts memory from 1.8GB to ~650MB with 3.2x throughput speedups on commodity AVX-512 CPU hardware with zero human-perceptible degradation in WER.
ADR-004: Ingress Transport — Full-Duplex WebSockets vs. HTTP Polling Decision: Selected persistent full-duplex WebSockets.
Rationale: Eliminates continuous connection handshake overhead and enables simultaneous bidirectional streaming of raw PCM audio chunks and neural audio response streams.
